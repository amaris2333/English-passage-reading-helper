## 0. TL;DR

- **9 条需求技术上 100% 可实现**，无一条需要付费授权，全套技术栈开源免费。
- **2 条必须妥协**：①「导入外刊 URL」纯前端必然失败（浏览器跨域），要借第三方抓取服务；②「PDF 导入」多栏/扫描件还原率 85~90%，必须配人工修正界面。
- **难点不在"能不能画出来"，而在"细节稳不稳"**：断句准确率、PDF 版面还原、笔迹坐标一致性、双语切换/聚焦时的页面跳动、长文渲染性能、PDF 导出的中文与分页。
- **最贵的难点是非技术的**：内置文章的译文 + 长难句标注 = 线性人力投入，是唯一会让预算翻倍的变量。
- **约 60% 底层能力该"拿来"**（pdf.js、ECDICT 词典、Web Speech、perfect-freehand、react-rnd、Intl.Segmenter），**40% 必须自研**（双语阅读交互编排、精读数据结构、导入修正界面、导出模板）。
- **建议**：先花 4~5 周做 MVP 给 10 个人用，别闭门做 10 周全量。P0 全量约 **40~48 人天**。

## 3.【重点】如何跟 AI 表达才能做出你想要的效果

### 3.1 五条总体原则

| # | 原则                       | 为什么（AI 最容易做歪的地方）                                                                                               |
| - | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 1 | **先锁数据模型，再谈界面**          | 你一上来就说"做个能点句子的阅读器"，AI 会把整段文字塞进一个 `<p>` 然后整段高亮。必须先命令它：`paragraphs:[{sentences:[{en,zh,analysis}]}]`，句子边界在数据层就存在 |
| 2 | **把"状态机"说清楚，而不是只说"点击"**  | "点击展开、再点收起"太模糊。要写清三态 + 每个状态下其他元素什么样（`display:none` 还是 `opacity:0.45`），否则会做成折叠动画、变灰、半透明等一堆"看起来实现了其实不对"的版本       |
| 3 | **对"隐藏""删除"加限定词**        | AI 听到"关闭编辑模式后笔记消失"，会老实 `clearRect()` 把笔迹删了。必须写"**隐藏 Canvas 图层，不销毁不清空，再次开启完整复原**"                               |
| 4 | **边界情况必须点名举例**           | 断句、导出、坐标这三类 AI 一定按最省事方式做（按 `.` 切、html2canvas 截屏、相对视口定位）。要主动喂反例：`U.S. / e.g. / don't`、`A4 分页不能断段`、`笔迹跟着内容滚动`    |
| 5 | **一次只做一个功能，并要求"先说验证方法"** | 一次性丢 9 条会生成一坨耦合代码。正确姿势：先 mock 数据跑通交互，再逐个接功能                                                                    |

> 你担心的三个典型跑偏，根因就是原则 1、2、3：**"能点击的句子"→整段高亮（原则1）；"中英对照"→逐句硬翻译（原则2，没定义对照粒度）；"笔记"→一次性截图（原则3，没区分隐藏与销毁）**

### 3.2 逐功能提示词模板（9 段，可直接复制）

#### ① 文章来源与导入（需求 1）

```text
【功能 1：文章来源与导入】
请实现一个文章导入模块，支持三种输入方式：1) 粘贴纯文本；2) 上传 PDF；3) 粘贴外刊 URL。

目标：无论哪种方式，最终都归一化为同一份数据结构：
{ title, source, tags:[], difficulty, paragraphs: [ "段落1文本", "段落2文本" ] }
段落顺序必须与原文一致。

交互：顶部工具栏"导入"按钮 → 弹出对话框，含三个 Tab（粘贴文本 / 上传 PDF / 输入链接）→ 确认后自动进入该文章的阅读页。

边界情况（必须处理）：
- PDF 解析后要合并被错误断行的句子：行尾没有句号且下一行首字母不是大写时，视为同一句，用空格连接。
- URL 抓取受 CORS 或反爬限制时，必须回退为"抓取失败，请直接粘贴正文"的中文提示，不允许静默失败或白屏。
- 空内容需提示；超过 10000 词需提示"文章过长，已截断"。

验收标准：我用一段含 3 个自然段的英文、一份 2 页 PDF 分别导入，两种方式的段落数与原文一致，且标题没有被混进第一段正文。
```

#### ② 双语对照开关（需求 2）

```text
【功能 2：双语对照开关】
目标：阅读区顶部有三档切换：全英文 / 中英对照 / 仅中文，默认"全英文"。

关键要求：
- 对照的最小单位是【句子】，不是段落，也不是逐词。禁止把整段英文下面糊一大段中文。
- "中英对照"模式下：先显示完整英文句，紧跟一行较小字号的灰色中文译文，句与句之间保留空行，视觉上能一眼看出哪句对哪句。
- 译文必须通顺、符合中文表达习惯，禁止机翻腔和逐字直译；专业术语首次出现可保留"中文（English）"形式。
- 译文不得改动英文原文任何一个字符。

交互：点击切换即时生效，不刷新页面、不丢失当前已展开的句子面板和手写笔迹。
边界：英文中含引号、破折号、括号、斜体的句子，译文要完整覆盖；空段落跳过；切换后页面滚动位置保持不变。

验收标准：切到"中英对照"后，英文句的数量与"全英文"模式完全一致且一一对应，没有串行或漏译；切回"全英文"后布局不发生跳动。
```

#### ③ 标签、难度与词数（需求 3）

```text
【功能 3：标签、难度与词数】
目标：
- 每篇文章有 1-3 个主题标签（如 人工智能 / 生物医药 / 气候变化 / 商业 / 心理学 / 科技）和 1 个难度标签（入门 / 进阶 / 挑战）。
- 文章正文第一行显示元信息条：【主题标签】【难度】总词数 1,243 词 · 预计阅读 6 分钟。

交互：左侧文章列表面板顶部有多选标签筛选器 + 难度下拉；筛选即时联动，支持"清空筛选"。
边界：
- 无标签的文章归入"未分类"，不能被筛选器吞掉。
- 词数统计规则：按空格分词并剔除纯标点；连字符词（state-of-the-art）算 1 词；缩写（U.S.、e.g.）算 1 词；撇号词（don't）算 1 词。
- 预计阅读时长 = 词数 / 200 分钟，向上取整。

验收标准：勾选"人工智能"后列表只剩带该标签的文章；文首词数与用 Word 统计的结果误差在 3% 以内。
```

#### ④ 句子级点击讲解（需求 4，本产品核心，务必完整复制）

```text
【功能 4：句子级点击讲解（本产品核心交互）】
目标：把每篇英文文章按【句子】切分成可交互单元，每个英文句子前面有一个小三角图标（▶ 未展开 / ▼ 已展开）。

交互流程（必须严格遵守）：
1. 初始态：全文正常显示，所有句子前是 ▶。
2. 点击某个句子的三角（或点击三角右侧的句子）：
   - 该三角变为 ▼，当前句加浅色底色高亮（不要改字号/行高，避免布局跳动）；
   - 除【当前句所在的那个段落】以外的其他段落全部隐藏（用 display:none，不是变灰、不是半透明、不是折叠动画）；
   - 当前段落中的其他句子保留显示，但透明度降到 0.45；被选中的句子保持 100% 不透明；
   - 在当前段落正下方插入"讲解面板"，包含两块内容：
     (a) 句型分析：第一行给出【句子主干】（主语 + 谓语 + 宾语/表语）；然后用分条形式拆解修饰成分（定语从句 / 状语从句 / 插入语 / 分词短语 / 同位语），每条写明"它修饰谁、在句中起什么作用"；用【主语】<谓语>（宾语）这类符号或不同底色区分成分，并在上方英文原句中同步高亮对应片段。
     (b) 重点短语与地道表达：列出 3-6 条，格式为 `短语 — 中文释义 — 例句（优先取自本文原句）`。
3. 再次点击同一个三角（或点击面板上的"收起"、或按 Esc）：讲解面板移除，其他段落完全恢复显示，三角回到 ▶，页面滚动位置与点击前一致。
4. 同一时刻只允许展开一个句子；点击另一个句子的三角时，自动收起上一个。

边界情况（必须处理）：
- 断句必须用正规的句子边界检测，不能简单按句号切分。U.S. / U.K. / e.g. / i.e. / Mr. / Dr. / Inc. / No. / etc. 中的点不是句子结尾；句末标点可以是 . ! ? 及其组合（?!"）；引号、括号内的句子要正确归属。
- 缩写与撇号不能被拆开：don't / it's / John's / can't 是一个整体。
- 一个句子跨越多行只算一个单元，三角只在该句开头出现一次。
- 段落首行缩进、列表项、小标题、图片说明不要被当成句子。
- 单词数少于 3 个的句子（如 "He said."）不提供讲解面板。
- 隐藏其他段落会导致页面变矮：请先记录当前句相对视口的位置，展开后把它滚动回同一位置，不允许它"跳"到屏幕外。

验收标准：
1) 点击任意句子的三角后，只有该句所在段落可见，其余段落完全不占空间；
2) 讲解面板出现，且主谓宾标注与英文原句片段一一对应；
3) 再点一次，页面恢复到点击前的样子，滚动位置不变；
4) 用测试句 "The U.S. economy, which grew 3% last year, didn't slow down — analysts say it won't." 验证：必须识别为【1】个句子，而不是 4 个。
```

#### ⑤ 单词卡（需求 5）

```text
【功能 5：单词卡】
目标：阅读区中每个英文单词都是可点击热区。鼠标左键单击单词 → 在点击位置附近弹出单词卡浮层。

卡片内容（自上而下）：
- 单词 + 音标（英音/美音可切换）+ 小喇叭按钮（点击朗读，用浏览器 speechSynthesis 或音频文件）
- 词性 + 中文释义（优先列本文语境下的义项，其余义项折叠）
- 难度标签（可并存多个）：四级 / 六级 / 考研 / 雅思 / 托福 / GRE / 专八，用彩色小圆角标签呈现
- 同义替换词 3-5 个，每个标注细微差别（如 formal / informal / 程度更强 / 偏书面），点击可跳转查询
- 本文原句（高亮该词）

交互：
- 触发：左键单击单词。注意与功能 4 不冲突——点击三角只触发句子面板，点击单词只触发单词卡，两者互不冒泡触发。
- 关闭：点击页面其他区域 / 按 Esc / 页面滚动超过 200px。
- 卡片不得超出视口，靠近右/下边缘时自动翻转方向。

边界：
- 连字符词、缩写、撇号词作为一个整体触发（state-of-the-art、don't）；单词前后的标点不算入单词。
- 句首大写的词要去大写后查原型；复数、过去式要还原词元再查。
- 在已展开讲解的句子里点单词时，单词卡与句子面板要能共存、不互相遮挡。

验收标准：点击 "significant" 能弹出含音标、释义、难度标签和至少 3 个同义词的卡片；点击 "don't" 时查询的是 don't 整体，而不是 don 和 t；朗读按钮能出声。
```

#### ⑥ 便签（需求 6）

```text
【功能 6：便签】
```

## 4.【重点】技术难点剖析（8 个硬骨头）

### 4.1 断句准确性 —— 准确率决定产品可信度

**本质**：句点是多义字符，既是句号，也是小数点、缩写点、省略号的一部分。  
例：`The U.S. economy, e.g. its GDP, grew 3.5% in Q1. Mr. Smith said "It's fine."` 有 6 个点，只有 2 个是真句号。纯正则实测错误率 8~15%，**每篇必错 1~2 处**，而精读场景下一处错误就被判定"这产品不行"。

| 方案                               | 准确率      | 成本            | 需后端           |
| -------------------------------- | -------- | ------------- | ------------- |
| 纯正则                              | 70~85%   | 1 人天 + 长期维护词表 | 否             |
| **`Intl.Segmenter` + 150 行规则兜底** | **95%+** | **1~1.5 人天**  | **否（零依赖零体积）** |
| spaCy / NLTK                     | 98%+     | 2 人天 + 引入后端   | 是             |

**推荐方案 ②**：`Intl.Segmenter('en',{granularity:'sentence'})` 底层是 ICU 断句规则，已内置 U.S./Mr./e.g./i.e./etc./Dr./Prof. 抑制。只需补四类兜底：①数字缩写 `No./Inc./Ltd./vs.` ②人名首字母 `J. R. R.` ③省略号与 `?!")` 组合 ④引号/括号归属。配 50~100 个 Vitest 回归用例。

> **防坑**：切完必须保留「人工断句修正」入口（句间点击即合并/分割）。95% 准确率意味着平均每篇仍错 1 处，与其追 100%，不如给用户一键修正。

### 4.2 PDF 版面还原 —— 准确率天花板 ~90%

**本质**：PDF 里**没有"段落"**，只有带坐标的文本碎片。人类看到的语义顺序在 PDF 中不存在。  
会遇到：①每行被切断（一个段落出来是 12 行碎片）②**双栏排版顺序错乱** ③页眉页脚混进正文 ④跨页连字符拆词。

**推荐解法**（2.5~~3 人天，双栏还原 85~~95%）：取文本块 x 中心做**直方图找峰谷自动判栏** → 按栏分组后 y 排序、行内 x 排序 → 相邻行间距突变处分段 → 在 ≥60% 页面顶部/底部重复出现的行判为页眉页脚剔除 → 跨页连字符修复。

> **防坑**：先扫一遍，拿不到文本层直接判为"扫描版"，友好报错并引导改粘贴或 docx。  
> **必须做**：配一个「导入后修正界面」（手动合并/切分段落、删噪声）。这不是偷懒，Readwise、Glasp、沉浸式翻译都这么做。**列为 P0 必选而非可选。**

### 4.3 Canvas 笔迹：坐标一致性 + 橡皮 + React 冲突

**本质**：笔迹在 Canvas 像素坐标里，内容在 DOM 流式布局里，**两者坐标系天生不一致**；且 Canvas 是命令式 API，React 是声明式渲染，重渲染可能冲掉已有笔迹。

| 子问题      | 推荐解法                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------- |
| 坐标存储     | **归一化坐标（相对内容容器 0~1）+ 记录绘制时容器宽高**，窗口缩放时线性映射                                                     |
| 画布层次     | **双层 Canvas**：固化层（已结束笔画）+ 实时层（正在画的一笔）                                                          |
| 橡皮       | **橡皮作为一类 stroke 记入数据**，回放时应用。可撤销/可重放/可跨设备还原。不用像素擦除                                             |
| React 冲突 | Canvas ref + 命令式绘制，`useEffect` 只初始化一次，组件 `memo` 化                                              |
| 触屏       | **Pointer Events + `touch-action:none`**，用 `getCoalescedEvents()` 提采样密度，同时支持鼠标/触屏/Apple Pencil |
| DPR      | `canvas.width = cssWidth * devicePixelRatio` 且 `ctx.scale(dpr,dpr)`                            |

> **这意味着什么**：笔迹存**结构化坐标**（每笔几十个数字，一篇 ~~200KB）可存几百篇；存 **PNG base64**（一篇 0.5~~3MB）存 5 篇就爆。**这个选择直接决定产品能装多少内容。**  
> **防坑**：`ResizeObserver` 监听容器 → 尺寸变化时按 scale 重放笔迹，**必须加 150ms 防抖**，否则拖窗口时每秒重放上百次。

### 4.4 笔迹层 vs 内容层的事件穿透（PM 与架构师共同标记的隐藏坑）

**本质**：笔迹 Canvas 要全图批注必须铺满内容区并接收指针事件，但这样就**吃掉了底下所有点击**——单词点不了、三角点不了。这是"同一区域服务两种互斥交互"。

**层叠规划（必须从一开始就统一，否则后期到处 `!important`）**：

```
内容层 z-0 → 句子高亮 z-5 → 笔迹层 z-10 → AI 侧栏 z-40 → 便签 z-45 → 单词卡 Portal z-50 → 弹窗 z-60
```

**推荐**：一期做「严格模式切换」（编辑模式开启 → 笔迹层 `pointer-events:auto`，内容交互禁用，单词卡自动关闭）；上线后按反馈再补「工具条三态：画笔/橡皮/选择」。

> **防坑（最致命）**：笔迹层关闭务必用 `visibility:hidden`，**绝不用 `display:none` / 卸载组件 / `clearRect`**——后者会让用户辛苦画的笔记当场阵亡。

### 4.5 单词卡：全文热区的性能陷阱

**本质**：直觉做法是"给每个单词包一个 `<span>` 绑事件"，但一篇 1500 词 = 约 1800 个 `<span>` + 1800 个监听器 + 数倍文本节点。**首屏明显卡顿、滚动掉帧**，而这一切只为取一个词。

**更优解法（不渲染词 span）**：

- 每个句子 = 一个文本节点（或一个 `<span data-sid>`）
- 鼠标抬起后用 `document.caretRangeFromPoint(x,y)`（Firefox 用 `caretPositionFromPoint`）拿到精确 caret
- 正则 `/[A-Za-z][A-Za-z'-]*/` 从 caret 向左右扩张得到词的 Range
- `range.getBoundingClientRect()` → 交 `@floating-ui` 定位

**收益**：DOM 节点 ~5000 → ~500，监听器 ~1800 → 1（事件委托）。省下后续所有性能优化人天。

**词形还原优先级**：ECDICT 原词 → `exchange` 字段反查（`p:ran/i:running`）→ compromise.js `toInfinitive()/toSingular()` → 自写变形规则 → 提示未收录。

> **防坑**：做 **200ms「悬停 ≠ 查词」判定**，必须区分"鼠标划过"和"点击"。否则用户复制整段时会疯狂弹卡。

### 4.6 PDF 导出：三条路线

| 方案                                      | 可选中/可搜索            | 中文                       | 分页                     | 含笔迹          | 工作量          |
| --------------------------------------- | ------------------ | ------------------------ | ---------------------- | ------------ | ------------ |
| ① **`window.print()` + `@media print`** | ✅ 完美               | ✅ 系统字体零问题                | ✅ `break-inside:avoid` | ⚠️ 需转 PNG 插入 | **3 人天** ✅推荐 |
| ② html2canvas + jsPDF                   | ❌ 全变图片，不可搜索/复制，放大糊 | ✅                        | ⚠️ 手动切片                | ✅            | 4~5 人天 备选    |
| ③ pdf-lib/jsPDF 自绘文本                    | ✅                  | ❌ 需手动嵌中文字体（3MB+），自己算换行分页 | ❌ 全手算                  | ✅            | 10+ 人天 ❌     |

**推荐**：①为主（写独立 `print.css`：隐藏导航/工具条/AI 球，白底，句子 `break-inside:avoid`，导出前 `await document.fonts.ready`）；含笔迹时把 Canvas 按段落高度区间切片成 PNG 绝对定位插入打印 DOM。

> **唯一体验妥协**：用户要在打印对话框多点一步「目标 → 另存为 PDF」。这是免费方案换来的唯一代价，非常划算。  
> **防坑**：导出弹窗放一行小字"在弹出的打印窗口中请选择『目标打印机 → 另存为 PDF』"。不写这句，80% 用户会当成 bug 反复反馈。

### 4.7 存储架构：localStorage 会撑爆（明确结论）

| 数据                | 单篇          | 100 篇     | 放得进 localStorage(5MB)？ |
| ----------------- | ----------- | --------- | ---------------------- |
| 文章 JSON（原文+译文+句析） | 20~80 KB    | 2~8 MB    | ❌ 临界/溢出                |
| 笔迹（结构化坐标）         | 100~300 KB  | 10~30 MB  | ❌ 溢出 2~6 倍             |
| 笔迹（PNG base64）    | 0.5~3 MB    | 50~300 MB | ❌ 爆 10~60 倍            |
| 裁剪版 ECDICT 词典     | 3~8 MB（一次性） | —         | ❌ 单独就爆了                |

**结论：一期就该上 IndexedDB，不要省。** 理由：①配额溢出是运行时异常，届时笔迹可能已写一半，回滚痛苦；②localStorage 是同步 API，长文场景掉帧；③`idb-keyval` 只有 600B，学习成本约 0.3 人天。

**分工**：IndexedDB 存文章库 / 笔迹（按 `articleId` 分片）/ 便签 / 生词本 / AI 历史 / 词典；localStorage 只放 UI 偏好（双语档位、字号、面板宽度、上次读到的位置、API Key）。

> **必配**：备份/恢复 JSON（建议从 P1 升 P0）。IndexedDB 在 Safari 无痕模式与用户清缓存时有被连带清理的风险，**没有备份 = 用户笔记随时可能一夜清零**。  
> **防坑**：3~~8MB 的词典 JSON 不要打进 JS 包，当静态资源懒加载 → 解析后写 IndexedDB，第二次启动秒开。否则首屏多等 3~~8 秒，用户以为网页坏了。

### 4.8 被严重低估的难点：内容供给 + 版权

**本质**：「内置文章」+「双语对照」+「长难句分析」+「重点短语」四项，技术上都是"读 JSON 渲染"，但**全部依赖巨额人工投入**，还可能撞版权。

| 素材来源                                                                           | 版权安全      | 推荐         |
| ------------------------------------------------------------------------------ | --------- | ---------- |
| 当代外刊付费媒体原文                                                                     | ❌ **高风险** | ❌ 不建议内置发布  |
| **公有领域 / CC 授权**（Project Gutenberg、arXiv、NASA、政府报告、官方演讲稿、VOA Learning English） | ✅         | ✅ **强烈推荐** |
| 自撰/改写/编译文章                                                                     | ✅         | ✅ 推荐       |
| 用户自己粘贴/导入的文章                                                                   | ✅         | ✅ 天然无风险    |

**生产管线**：Node 脚本批量调 LLM 生成「译文 + 句析 + 短语」初稿 → 输出 CSV 供人工校对 → 校对通过打包 JSON。单篇 AI 初稿约 15 分钟 + 人工校对 30~60 分钟。**10 篇 ≈ 2 人天，50 篇 ≈ 8~10 人天。**

> ⚠️ **红线**：**不要用付费媒体原文做"内置文章库"公开发布。** 建议改公有领域/CC 素材，或把产品定位改成"用户自己导入外刊的工具"，内置库只放少量样例。忽视这条，后面可能不得不整体下架。

### 5.4 拿来 vs 自研的三条法则

| 法则                  | 内容                                                     | 示例                                                                              |
| ------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------- |
| **1. 商品化 vs 差异化**   | 别人也做得到、用户感知不到差别的能力 → **一律拿来**；用户选择你而非别人的理由 → **必须自己写** | 拿来：PDF、词典、画线、拖拽、存储。自研：**双语阅读交互编排**（句子聚焦/复原/锚点协同）、**精读数据结构**、**导入修正界面**、**导出模板** |
| **2. 运行时 vs 构建时**   | 结果稳定、只算一次的事 → **挪到离线/构建期**；运行时只保留即时交互                  | 译文、长难句分析、短语卡、内置文章清洗 → 全部离线预生成打包。**这直接省掉所有延迟、成本和 AI 出错的信任风险**                    |
| **3. 不可替代性 × 失效成本** | 挂了会导致主流程崩的能力（LLM）必须有降级 + 清晰失败提示；纯辅助能力（TTS）可随时替换        | LLM 挂了 → 降级为"稍后重试 + 保留已输入内容"；TTS 不可用 → 静默显示音标即可                                 |

> **一句话**：底层（PDF、词典、发音、画线、拖拽、存储）**全用开源的**，约 60%；中间层（数据结构、精读交互、导入修正、导出模板）**必须自己写**，约 40%。**别在底层重复造轮子，也别把灵魂外包给 AI 实时生成。**

### 6.1 选型清单（摘要）

| 词典     | **ECDICT 裁剪版**                       | dictionaryapi.dev      | 自带考试难度标签                             |

### 6.2 核心数据模型（精简版）

```ts
export type DisplayMode = 'en' | 'bilingual' | 'zh';
export type ExamTag = 'cet4' | 'cet6' | 'ky' | 'ielts' | 'toefl' | 'gre' | 'gmat';

export interface Sentence {
  id: string;              // `${articleId}-p${pi}-s${si}` ← 全局唯一的"锚"
  index: number;
  en: string;
  zh?: string;
  wordCount: number;
  zhSource: 'none' | 'ai' | 'human';
  analysis?: SentenceAnalysis;
  phrases?: Phrase[];
}

export interface SentenceAnalysis {
  pattern?: string;        // "S + V + O + that-clause"
  skeleton?: string;       // "AI models (S) are reshaping (V) education (O)"
  chunks: Chunk[];         // 驱动"标注主谓宾"UI
  generatedBy: 'rule' | 'llm' | 'human';
  reviewed?: boolean;      // 是否人工校对过（强烈建议保留）
}

export interface Chunk {
  role: 'S' | 'V' | 'O' | 'C' | 'M' | 'Clause' | 'Appositive' | 'Insert';
  text: string;
  start: number; end: number;   // 相对 sentence.en 的字符偏移（用于高亮）
  note?: string;
}

export interface Paragraph { id: string; index: number; sentences: Sentence[]; heading?: string; isNoise?: boolean; }

export interface ArticleMeta {
  tags: string[]; difficulty: 1|2|3|4|5;
  wordCount: number; sentenceCount: number; readMinutes: number;
  sourceUrl?: string; license?: string;      // 版权字段必备
}

export interface Article {
  schemaVersion: number; id: string; slug: string;
  title: string; titleZh?: string; source: string;
  sourceType: 'builtin' | 'paste' | 'pdf' | 'url';
  meta: ArticleMeta; paragraphs: Paragraph[];
}

// 笔迹：务必存结构化坐标，禁止存 PNG
export interface InkPoint { x: number; y: number; p: number; }   // x/y 归一化 0~1
export interface Stroke { id: string; tool: 'pen'|'eraser'|'highlighter'; color: string; size: number; points: InkPoint[]; }
export interface InkDoc { articleId: string; baseWidth: number; baseHeight: number; strokes: Stroke[]; }

export interface ExportConfig {
  lang: 'en' | 'bilingual' | 'zh';
  includeAnalysis: boolean; includePhrases: boolean;
  includeInk: boolean; includeNotes: boolean;
  filename: string;
}
```

**句子边界必须在数据层存在`Sentence.id`** —— 这是整个产品的地基，后期补要重构全部。

## 8. 三个决策点（最大程度影响成本与工期）

### 决策点 1｜内置文章怎么来？——「内容，还是工具？」

> **唯一可能让预算翻倍的问题。技术上很简单，钱在这里。**

| 选项              | 说明                                            | 标注成本                         | 推荐    |
| --------------- | --------------------------------------------- | ---------------------------- | ----- |
| **A. 工具优先（推荐）** | 内置 2~3 篇精校样板做示范，核心定位是"**让你导入自己想读的文章**"，版权风险归零 | ≈ 1 人天                       | ⭐⭐⭐⭐⭐ |
| B. 中等内置库        | 内置 10~15 篇（AI 初稿 + 人工校对）                      | ≈ 2~3 人天 + 持续更新              | ⭐⭐⭐⭐  |
| C. 大型内容库        | 内置 50+ 篇完整标注                                  | ≈ 10~15 人天且持续投入，**版权风险显著上升** | ⭐⭐    |

**推荐 A 起步，跑通后按 B 迭代。** 外刊精读的核心价值是"用户有自己想读的文章"，内置库是营销钩子不是核心。**先花钱造工具，再决定是否花钱造内容，顺序反了会很痛。**

### 决策点 2｜要不要加一层"很薄的后端"？

| 选项               | 能做到                               | 做不到                   | 成本               | 推荐      |
| ---------------- | --------------------------------- | --------------------- | ---------------- | ------- |
| **A. 纯前端**       | P0 全部、笔迹、便签、导出、AI 问答（自填 Key）      | URL 导入、多端同步、Key 服务端保护 | **0 元运维**        | ⭐⭐⭐⭐⭐   |
| B. Serverless 中转 | A 全部 + **URL 导入** + **Key 服务端代理** | 真正的多用户账号              | +3~5 人天，月成本几十元   | ⭐⭐⭐（二期） |
| C. 完整后端 + 账号     | 全部 + 多端同步                         | —                     | +10~15 人天 + 持续运维 | ⭐       |

**推荐一期 A，但所有外部调用走统一 `apiClient` 抽象，留好 B 的接口。**

> ⚠️ **副作用必须知道**：纯前端 + 自填 Key 意味着**分享给别人用时，每个人都要自己去申请 Key**。自用/小圈子完全 OK；**若目标是做成给很多人用的产品，答案相反：一期就该上 B。**

### 决策点 3｜首版做多全？——「先发布，还是先完美」

| 选项                  | 范围                                                         | 工期        | 上线      | 推荐    |
| ------------------- | ---------------------------------------------------------- | --------- | ------- | ----- |
| **A. MVP 先行（强烈推荐）** | 决策点1-A + 第1期：粘贴/PDF 导入、双语切换、点句聚焦、点词出卡 + 2 篇样板。**笔迹和导出先不做** | **16~18** | 4~5 周   | ⭐⭐⭐⭐⭐ |
| B. P0 全量            | 含笔迹批注 + PDF 导出                                             | 33~36     | 8~9 周   | ⭐⭐⭐   |
| C. 一次性全做（含 AI）      | A+B+AI 问答                                                  | 40~48     | 10~12 周 | ⭐⭐    |

**推荐 A。** 这类产品的失败通常不是"功能不够"而是"交互细节没打磨"。先让 10 个种子用户用 MVP 读 3 篇文章，你拿到的反馈比闭门 3 个月更有价值。

## 9. 待确认问题（12 条，附默认建议）

| #  | 问题                      | 默认建议                                                                        |
| -- | ----------------------- | --------------------------------------------------------------------------- |
| 1  | **内置文章来源与版权**           | 改用公版/CC 素材（Gutenberg、arXiv、NASA、VOA Learning English）或自撰范文，内置 6~8 篇         |
| 2  | **外刊链接导入**              | 一期砍掉（降 P2），只做粘贴 + PDF。若要保留，借 r.jina.ai                                      |
| 3  | **译文预生成还是实时调 AI**       | **预生成入库**。内置文章离线生成写进 JSON；导入文章在导入时**一次性批量生成**并缓存。**绝不阅读时逐句实时请求**            |
| 4  | **长难句/单词卡/同义词：预生成还是实时** | 混合：句析预生成（导入文章首次点击生成 + 永久缓存）；单词释义与难度标签接 ECDICT 本地查表（零成本零延迟）；同义词本地优先，查不到才调 AI |
| 5  | **AI 问答的后端与 Key**       | 纯前端 + 用户自填 Key（存 localStorage），未填给友好引导                                      |
| 6  | **单页应用还是带后端 / 要不要账号**   | 一期纯前端 SPA 无账号，数据层预留接口                                                       |
| 7  | **导出 PDF 路径**           | 优先 `window.print()` + 打印样式表；若坚持"点击直接下载文件"再上 jsPDF                           |
| 8  | **移动端适配**               | 一期只保桌面 + iPad 横屏。单词卡触发改"长按/点选"                                              |
| 9  | **难度系数怎么定义**            | 公式自动算（平均句长 + 生词率 + 从句密度）+ 人工微调，映射入门/进阶/挑战                                   |
| 10 | **主题标签谁来打**             | 内置人工预设；导入由 AI 自动打 1~3 个，用户可编辑。先固定 8 个标签，避免发散                                |
| 11 | **发音能力**                | 默认 Web Speech API，不自建 TTS                                                   |
| 12 | **同义词要不要详细辨析**          | 一期只给 3~5 个 + 语体/程度标注，不做长篇辨析                                                 |

## 10. 风险登记表

| 优先级   | 风险                       | 后果           | 缓解                                                    |
| ----- | ------------------------ | ------------ | ----------------------------------------------------- |
| 🔴 P1 | **内置付费外刊原文的版权风险**        | 产品可能下架       | 改公有领域/CC 素材；或定位为"用户自带内容工具"；`meta.license` 字段必备        |
| 🔴 P1 | **内容生产成本失控**             | 预算翻倍         | LLM 预生成 + 人工校对；一期只做 2~3 篇样板                           |
| 🔴 P1 | **笔迹数据丢失**（重渲染/存储溢出/清缓存） | 用户笔记清零，最致命差评 | 结构化存 IndexedDB + `visibility:hidden` 不销毁 + **备份导出必做** |
| 🟡 P2 | PDF 多栏还原不准               | 阅读体验差        | X 轴判栏 + **导入后修正界面（P0 必选）**                            |
| 🟡 P2 | 断句偶发错误                   | 被判"不专业"      | 95% 自动 + 人工合并/切分入口 + 回归测试集                            |
| 🟡 P2 | LLM 端点 CORS 不通           | AI 功能不可用     | 开工第一周先实测；baseURL 可配；默认聚合网关                            |
| 🟡 P2 | 存储溢出                     | 运行时异常        | 一期直接 IndexedDB（仅 0.3 人天）                              |
| 🟢 P3 | 长文渲染性能                   | 滚动掉帧         | 不渲染词 span（Range 反查）+ 段落懒挂载                            |
| 🟢 P3 | API Key 本地存储安全           | Key 泄露       | 提示用小额专用 Key；依赖精简；二期转服务端代理                             |

**三条不可妥协的体验红线**：
